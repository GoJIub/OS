# 1. Два уровня выделения памяти

Судя по первой схеме, преподаватель объясняет, что в ОС существует **два основных уровня управления памятью**:

## 1.1. Выделение памяти ядром

Это операции на уровне ядра ОС — грубо говоря, управление **страницами физической памяти**.
Типичные интерфейсы:

* `sbrk/brk`
* `mmap`
* системные вызовы ядра, выдающие **страничные блоки** (обычно 4 КБ или кратно).

Характеристики:

* дорого по времени (системный вызов, переключение контекста);
* выдает память крупными страницами;
* гарантирует изоляцию и защиту процессов.

На доске это подписано как:

**Память ядра ←→ СТР (система распределения)**
и стрелка к некоторому стеку страниц.

## 1.2. Выделение памяти пользовательской (страничной) подсистемой — malloc

Второй уровень — **пользовательский аллокатор**, например glibc `malloc`, jemalloc, tcmalloc.

Он работает **поверх страниц**, выделенных у ядра, и делает мелкое распределение:

* дробит большие страницы на блоки;
* ведёт списки свободных блоков;
* занимается слиянием, разбивкой, выделением и освобождением.

Именно этот уровень обеспечивает удобный интерфейс:

```c
void* a = malloc(50);
free(a);
```

На доске это обозначено как:

**Страничная подсистема / malloc**
которая взаимодействует со страницами, полученными из ядра.

---

# 2. Метрики (критерии качества) стратегий распределения

На втором фото виден список:

1. **Фактор использования:**
   `Vреал / Vидеал`
   или степень фрагментации.

Это ключевая метрика:

* **реально выделенный объём** / **идеально необходимый объём**.
  Чем ближе к 1 — тем меньше фрагментация.

2. **Скорость**
   Оценивается:

* скорость выделения;
* скорость освобождения;
* стоимость внутреннего обслуживания структур.

Особенно важна для серверов с высокой нагрузкой.

3. **Удобство (простота)** использования
   Речь про то, чтобы аллокатор была легко использовать и внедрять:

* простой API (`malloc`, `free`, `realloc`);
* способность перераспределять память;
* безопасность (выявление ошибок: double free, overflow).

# 3. Классические стратегии выделения памяти

На фотографиях несколько схем:
— пример непрерывного массива 16 КБ,
— три malloc(50),
— схема блоков степеней двойки.

Ниже — восстановление теории.

---

# 3.1. Простое линейное выделение (arena allocation)

Используется, когда есть один большой буфер (например 16 КБ) и указатель "текущей позиции".
Схема показывает:

```
0 ... 50 ... 100 ... 150 ... конец
```

При `malloc(50)` двигается указатель.
Преимущества:

* максимальная скорость (просто смещение указателя);
* отсутствие фрагментации.

Недостатки:

* нет `free`, или освобождение возможно только **в обратном порядке** (как стек).

---

# 3.2. Списки свободных блоков (free lists)

Если область памяти допускает освобождение, то начинают возникать дыры.

На доске показано:

* три malloc по 50 байт,
* затем один освобождается,
* появляется свободный блок посередине.

Это ведёт к **внешней фрагментации**.

Стратегии работы с такими блоками:

### 3.2.1. First fit

Выбрать первый подходящий свободный блок.

### 3.2.2. Best fit

Выбрать наименьший блок, куда помещается запрос.
Лучше по степени использования, но медленнее.

### 3.2.3. Worst fit

Выбрать самый большой свободный блок.
Обычно неэффективен.

---

# 3.3. Аллокаторы на основе степеней двойки (buddy system)

На четвёртом фото — таблица:

```
16
32
64
128
...
```

И справа — цепочки свободных блоков (free lists).

Аллокатор округляет запрос вверх до ближайшей степени 2:

Пример с доски:

```
a = malloc(50)
→ округляется до 64 байт
```

В списке 64 ищется свободный блок.
При освобождении блок может быть объединён с "buddy" — парным блоком, если он тоже свободен.

Преимущества:

* быстрое объединение;
* простые структуры данных.

Недостатки:

* значительные внутренние избыточные расходы (округление может давать до 100% перерасхода).

---

# 3.4. Сегрегированные списки (segregated lists)

То, что на доске справа:

```
32:
  [ ][ ][ ][ ]...
```

Это множественные списки свободных блоков разных размеров.

Механизм:

1. Размер запроса округляется до ближайшего класса (например 32, 64, 128).
2. Выбор из соответствующего списка.

Часто используется в производительных аллокаторах (jemalloc, tcmalloc).

---

# 3.5. Смешанные и продвинутые стратегии

Современные аллокаторы используют комбинации:

* сегрегированные классы для маленьких объектов;
* большие объекты выделяются через отдельные `mmap`;
* кэш объектов (thread local cache) для ускорения работы в многопоточных средах.

Также учитываются:

* NUMA;
* локальность кешей;
* конкуренция потоков.

---

# 4. Пример механики работы malloc (из изображений)

1. При первом `malloc` аллокатор запрашивает у ядра большую страницу (или несколько).
2. Делит её на блоки.
3. Поддерживает списки свободных блоков.
4. При `free` блок возвращается в соответствующий список.
   Иногда происходит слияние (coalescing).

На доске есть запись:
`free(a, 50)` — намек на то, что можно реализовать free с указанием размера (как в некоторых специализированных аллокаторах), что ускоряет освобождение.

Ниже — строгое, структурное и техническое сравнение **стратегии McKusick (bucket allocator)** и **buddy allocator**, с выделением ключевых отличий, включая те, что обычно не упоминаются в учебниках.

---

# 1. Общая идея систем

## Buddy allocator

* Оперирует **памятью большими непрерывными участками**.
* Разбивает память на блоки степеней двойки **динамически**, с возможностью разбиения и слияния.
* Ключевая идея — наличие **buddy-пары**: два соседних блока одного размера, которые могут быть объединены.

## McKusick allocator (BSD malloc)

* Работает на уровне **малых выделений** в пользовательском пространстве.
* Основан на **фиксированных классах размеров (buckets)**, каждый — степень два.
* **Страницы заранее делятся на одинаковые блоки** одного класса.
* Нет механизма динамического объединения блоков.

---

# 2. Табличное сравнение

| Критерий                         | McKusick (BSD malloc)                         | Buddy allocator                                |
| -------------------------------- | --------------------------------------------- | ---------------------------------------------- |
| **Основной объект управления**   | Малые блоки (16, 32, 64, 128…) внутри страниц | Крупные области памяти (до MB)                 |
| **Разметка страницы**            | Страница заранее дробится на одинаковые блоки | Страница разрезается *по мере запроса*         |
| **Округление размера**           | До класса (bucket): 16, 32, 64 …              | До степени двойки (иногда более крупной)       |
| **Фрагментация внутренняя**      | Значительная (блок фиксированного размера)    | Меньше, но не нулевая                          |
| **Фрагментация внешняя**         | Нулевая для малых объектов                    | Возможна и регулярно возникает                 |
| **Coalescing (слияние)**         | Отсутствует                                   | Основной механизм buddy                        |
| **Скорость выделения**           | Максимальная: O(1)                            | O(log N) из-за поиска buddy                    |
| **Скорость освобождения**        | O(1)                                          | O(log N) из-за возможного слияния              |
| **Потеря памяти при округлении** | Может быть большой на мелких объектах         | Меньше, но зависит от спроса                   |
| **Назначение**                   | malloc в пользовательском пространстве        | ядерный аллокатор страниц или больших структур |

# 3. Ключевые различия «в сути механизма»

## 3.1. Buddy — система **динамического разбиения и слияния**

Buddy работает так:

1. Запрос 70 → округляется до 128.
2. Если есть блок 256, он *делится* на два по 128.
3. При освобождении два «buddy»-блока могут быть *объединены обратно*.

То есть buddy — **алгоритм рекурсивного деления/склеивания памяти**.

### McKusick так *не делает*.

Страницы не соединяются и не режутся динамически:

* Страница bucket'а 64 **навсегда остаётся набором блоков по 64**.
* Освободившиеся блоки просто возвращаются в free-list.

Это фундаментальное отличие.

---

## 3.2. McKusick использует **страничные пулы**, buddy — **единую структуру памяти**

Buddy управляет огромной областью (часто — всем физическим адресным пространством) и позволяет:

* отдавать большие блоки,
* затем разрезать их на маленькие по потребности,
* сливать фрагменты обратно.

McKusick:

* получает от ОС уже выделенные **страницы** (или несколько),
* закрепляет каждую страницу за определённым bucket,
* блоки разных размеров никогда не смешиваются в одной странице.

---

## 3.3. Производительность

### McKusick:

Выделение:

```
— взять голову списка bucket'a
— вернуть её
```

Освобождение:

```
— вернуть блок в соответствующий список
```

Абсолютно O(1).
Именно поэтому BSD malloc был очень быстрым.

### Buddy:

Выделение:

* иногда делит блоки,
* иногда ищет более крупный блок.

Освобождение:

* пытается выполнить рекурсивное слияние.

Сложность всегда хуже (O(log N)).

---

## 3.4. Борьба с фрагментацией — противоположные подходы

### Buddy

Пытается контролировать **внешнюю фрагментацию**.
Слияние buddy-блоков позволяет восстановить большие непрерывные области.

### McKusick

Исключает внешнюю фрагментацию полностью, но ценой **внутренней фрагментации**:

Если нужно 33 байта — выдают 64.

---

# 4. Практическое предназначение различается

| Buddy                                     | McKusick                                      |
| ----------------------------------------- | --------------------------------------------- |
| Используется в ядрах ОС                   | Используется в malloc                         |
| Управляет **страницами**                  | Управляет **мелкими объектами**               |
| ОС выделяет большие структуры             | Пользователь выделяет строки, массивы, списки |
| Требует аккуратного контроля фрагментации | Требует высокой скорости                      |

Аллокатор McKusick строится поверх buddy или mmap/sbrk.

---

# 5. Простая образная аналогия

### Buddy

Как склад, где большие коробки можно разрезать пополам, а потом снова соединить, если обе половины пусты.

### McKusick

Как магазин, где для каждого типа товаров есть свой ящик (bucket).
Ящик на 64 ячеек всегда остаётся ящиком на 64 — он не превращается в ящик на 32 или 128.

**Слябовый аллокатор (Slab Allocator)** по Таненбауму/Вахалии — это высокопроизводительный механизм управления памятью, применяемый в операционных системах (напр. Solaris, Linux, MINIX). Он предназначен для **быстрого выделения и освобождения множества объектов фиксированного размера** — структур ядра: процессов, сокетов, inode, дескрипторов файлов и т.п.

Ниже — простое и точное объяснение в духе Таненбаума/Вахалии.

---

# Идея слябового аллокатора

Проблема обычных аллокаторов:

* частые выделения/освобождения маленьких объектов → **фрагментация**, большие накладные расходы;
* нужен механизм, который быстро выдаёт готовые объекты одинакового размера.

**Решение — выделять память крупными блоками (“slabs”) и хранить в них готовые экземпляры объектов.**

---

# Основные сущности

### 1. **Кэш объектов (cache)**

Для каждого типа объекта (inode, PCB, mutex и др.) ядро создаёт **кэш**:

```
cache_inode
cache_process
cache_mutex
...
```

В кэше хранятся:

* *конструктор* — функция инициализации объекта,
* *деструктор* — функция очистки,
* список slab’ов.

То есть кэш — это фабрика объектов.

---

### 2. **Slab**

Slab — это **физически непрерывный блок памяти**, разбитый на слоты одинакового размера.

Например, slab для `inode`:

```
---------------------------------
| inode | inode | inode | inode |
---------------------------------
```

У каждого slab есть состояние:

* **полный** (все слоты заняты),
* **частичный** (есть свободные),
* **пустой**.

Slab в состоянии “частичный” — наиболее полезный: именно из него выдаются новые объекты.

---

### 3. **Объект**

Внутри slab объекты могут быть:

* свободные,
* занятые.

Slab allocator управляет списком свободных объектов через **free list**.

---

# Как работает выделение памяти

1. В кэше ищется slab в состоянии **частичный**.
2. Из его free-list берётся готовый объект.
3. Если таких нет → ищется **пустой slab**.
4. Если и его нет → аллокатор запрашивает у системы новый блок памяти (обычно через buddy-аллокатор).

Выдача объекта — **O(1)**.

---

# Как работает освобождение

1. Объект возвращается в slab и добавляется в free-list.
2. Если slab стал пустым → может быть возвращён системе (в зависимости от политики).

Освобождение — **O(1)**.

---

# Зачем нужны конструкторы и деструкторы?

Чтобы не делали дорогостоящую инициализацию каждый раз.

Например, выделили 1000 структур `inode`:

* один раз инициализировали все слоты (конструктор),
* затем просто раздаём готовые объекты.

Это ускоряет выделение в десятки раз.

---

# Почему это лучше обычных malloc/free?

| Метод               | Проблемы                                                            | Slab решает? |
| ------------------- | ------------------------------------------------------------------- | ------------ |
| **malloc/free**     | много накладных операций, фрагментация, разные размеры объектов     | ✔ Да         |
| **buddy-allocator** | быстрый, но выделяет крупные блоки, не подходит для мелких объектов | ✔ Да         |
| **slab allocator**  | выдаёт маленькие, идентичные объекты моментально                    | —            |

Преимущества slab-аллокатора:

* почти нет фрагментации,
* очень быстрый O(1) доступ,
* объекты заранее инициализированы,
* кэширование улучшает локальность данных.

---

# Мини-иллюстрация

Допустим, объект — структура размером 64 байта, slab — 4096 байт:

```
slab (4096 bytes)
---------------------------------
| 64 | 64 | 64 | ... | 64 bytes |
---------------------------------
    64 objects total
```

Если нужно создать процесс — ОС просто выдёргивает готовую структуру из free-list.

* избегать фрагментации,
* увеличить скорость выделения,
* упрощать управление памятью,

# 6. Таблица страниц и трансляция виртуального адреса

На нескольких фотографиях изображена структура записи таблицы страниц (PTE — Page Table Entry):

| P | Номер физ. страницы | Защита | W | R |

Где:
-	P (Present bit) — страница присутствует в физической памяти.
Если P = 0, возникает page fault — требуется подгрузка страницы из backing store (обычно файл подкачки).
-	Номер физической страницы — индекс фрейма физической памяти.
-	Биты защиты:
    -	R — разрешение на чтение,
    -	W — разрешение на запись,
    -	иногда — X (execute), U/S (user/supervisor).

Запись таблицы страниц определяет, как виртуальный адрес преобразуется в физический, и можно ли производить операцию (читать/писать/исполнять).

# 7. Формат виртуального адреса

На фото видно:

ВA = | номер ВС | смещение внутри страницы |

ВС = виртуальная страница (Virtual Page Number)

Смещение — младшие биты, не меняются при трансляции.

# 8. TLB — Translation Lookaside Buffer

На фото изображён TLB и стрелка от виртуальной страницы к TLB.

## 8.1. Что делает TLB

TLB — маленький высокоскоростной кеш для запросов трансляции:

VPN → PFN
(virtual page number → physical frame number)

При обращении к памяти:
1.	Извлечь номер виртуальной страницы (VPN).
2.	Проверить TLB.
3.	Если hit — мгновенно получить номер физической страницы (PFN).
4.	Если miss — выполнить обращение к таблице страниц, загрузить PTE в TLB.

## 8.2. Плохие случаи
-	TLB miss вызывает многократное обращение к памяти.
-	Если PTE говорит P = 0 → page fault.

На доске показано, что TLB существенно ускоряет доступ, снижая частоту обращений к медленной таблице страниц.

⸻

# 9. Page Fault: цепочка обработки

Судя по схеме:
```
TLB miss →
  Таблица страниц →
    бит присутствия = 0 →
       обращение к ПЗУ/диску →
         загрузка страницы →
           обновление таблицы страниц →
             обновление TLB →
               продолжение выполнения
```

Полный цикл:
1.	Процесс обращается по виртуальному адресу V.
2.	TLB miss → ОС ищет PTE.
3.	PTE.Present = 0 → нет страницы в RAM.
4.	ОС выбирает жертву — страницу физической памяти для вытеснения.
5.	Если страница-жертва модифицирована — её записывают в файл подкачки (swap).
6.	Загружается нужная страница.
7.	PTE обновляется (Present=1, PFN=…).
8.	TLB обновляется.
9.	Инструкция перезапускается.

Это — основа виртуальной памяти.

⸻

# 10. Алгоритмы замещения страниц

На последних фото препода объясняет:
	•	FIFO
	•	NRU
	•	LRU
	•	Aging (алгоритм старения)

Далее — подробное описание, согласованное с рисунками.

⸻

## 10.1. FIFO (First-In, First-Out)

Нарисована цепочка страниц:

[R:0] → [R:0] → […]

Смысл:
-	когда требуется вытеснение, выбирают страницу, которая находится в памяти дольше всех.

Преимущества:
-	простейшая реализация — очередь.

Недостатки:
-	может вытеснять часто используемые страницы → “Belady’s anomaly” — увеличение количества фолтов при увеличении RAM.

⸻

## 10.2. NRU (Not Recently Used)

Согласно рисунку, страницы классифицируются по двум битам:

R (Reference bit)
W (Modified/Dirty bit)

Четыре класса:
1.	R=0, W=0 — не использовалась, не модифицирована (лучший кандидат)
2.	R=0, W=1 — не использовалась, но модифицирована (дороже — требует записи)
3.	R=1, W=0 — использовалась, но чистая
4.	R=1, W=1 — использовалась и модифицирована (худший кандидат)

NRU выбирает случайно среди наиболее “низкого” класса, который не пуст.

На фото справа указано:

t = 0.5 c

Это означает периодическое обнуление битов R, чтобы обновлять информацию об использовании.

⸻

## 10.3. LRU (Least Recently Used)

В последнем фото видно:

LRU
C ← (C << 1) + R

Это похоже на алгоритм aging, но его объясняют как приближение LRU.

Истинный LRU

Хранить точный порядок использований крайне дорого (например, стек ссылок). Обычно LRU эмулируют, а не реализуют напрямую.

⸻

## 10.4. Aging — аппаратная/программная аппроксимация LRU

На доске изображён регистр C для каждой страницы:

C = C >> 1 + (R << (n-1))
или
C = (C << 1) + R

Это два варианта одного алгоритма.

Механизм aging:
1.	Для каждой страницы есть счётчик «старости» C (8 или 64 бита).
2.	Периодически (каждые t мс):
	-	C сдвигается,
	-	в крайний бит записывается R,
	-	бит R сбрасывается.

Чем меньше значение C — тем страница реже использовалась → она — кандидат на вытеснение.

Пояснения из рисунков:
-	R пришёл от линии памяти при обращении.
-	Каждые t секунд «старение» обновляет все C.
-	В итоге C содержит историю обращений за последние N интервалов.

Aging — почти идеальная аппроксимация LRU при низких затратах.

⸻

# 11. Соотношение алгоритмов замещения

Алгоритм |	Аппаратная поддержка |	Качество выбора	| Стоимость |
-------- | --------------------- | ---------------- | ----------
FIFO |	не требует |	низкое |	минимальная
NRU |	требует | R,W |	среднее	низкая
LRU |	требует сложных структур |	высокое | 	высокая
Aging |	требует R |	близко к LRU |	умеренная


⸻

# 12. Итоговая интеграция теории

Теперь у нас сложилась полная картина:
1.	Виртуальный адрес состоит из номера виртуальной страницы и смещения.
2.	Страничная таблица хранит отображение VPN→PFN и права доступа.
3.	TLB ускоряет трансляции; при miss — обращение к таблице страниц.
4.	Page Fault приводит к загрузке страницы из диска и возможному вытеснению другой страницы.
5.	Алгоритмы замещения страниц определяют, какую страницу удалить при нехватке физической памяти:
	-	FIFO — простейший.
	-	NRU — использует биты R и W.
	-	LRU — минимизирует фолты, но дорог.
	-	Aging — дешёвая аппроксимация LRU.
6.	Все битовые схемы и временные циклы на доске относятся к механизму обновления битов R и регистров C — компонентам NRU и алгоритма aging.
