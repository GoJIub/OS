## Короткая сводка (что в итоге)

* `gcc -fPIC -c foo.c -o foo.o` — генерируется **объектный файл** ELF (`ET_REL`) с секциями `.text`, `.data`, `.bss`, `.rodata`, `.rela.*`, `.symtab` и т.д. В нём есть **рело́кации** — места, где адреса ещё неизвестны, и отсылки по именам к символам.
* `gcc -shared foo.o -o libfoo.so` — линкер собирает объектники, создаёт **ELF shared object** (`ET_DYN`) с динамической секцией `.dynamic`, динамической таблицей символов `.dynsym`, табличками хэшей, таблицами релокаций `.rela.dyn`, `.rela.plt`, PLT/GOT и (опционально) SONAME. В `.so` могут остаться нерезолвенные внешние символы — они будут разрешаться при `dlopen`/загрузке.

Теперь — по порядку.

---

## 1) Объектный файл `.o` (что и как создаётся при `-c`)

### Команда

```bash
gcc -fPIC -c foo.c -o foo.o
```

### Что происходит внутри компилятора (front-end + back-end)

1. **Лексический/синтаксический разбор** → AST.
2. **Генерация промежуточного кода** → оптимизации → генерация машинного кода.
3. **Генерация объектного файла** в формате ELF `ET_REL` (релятивный объект).

### Что находится в `foo.o`

* Секции:

  * `.text` — машинный код функций.
  * `.rodata` — константы/строки.
  * `.data` — инициализированные глобальные переменные.
  * `.bss` — неинициализированные глобальные переменные (нет данных в файле, только размер).
  * `.symtab` / `.strtab` — таблица символов (имён) для линкера и отладчика.
  * `.rela.<sec>` (или `.rel.<sec>`) — **релокации**: записи, которые говорят «в этом смещении в секции нужно поставить адрес символа X, когда он станет известен».
  * `.debug_*` (опционально) — отладочная информация.
* В объектнике всё адреса ВРЕМЕННЫ (relative). Там хранятся *символьные ссылки* — имя символа и тип релокации (каким образом нужно вставить адрес позже).

### Почему нужен `-fPIC`

* `-fPIC` (Position Independent Code) просит компилятор генерировать код, который **не содержит абсолютных адресов** в коде (или минимально), а использует относительные обращения (RIP-relative на x86_64) и индирекции через GOT для глобальных переменных.
* Без `-fPIC` компилятор может сгенерировать инструкции, требующие фиксации (записи в текстовый сегмент при загрузке) — это называется *text relocations* и плохо: нарушает W^X, мешает совместному использованию кода разными процессами и плохо портируется.
* PIC обычно чуть медленнее (индирекции), но даёт корректное поведение для .so.

### Релокации в `.o`

* Каждая релокация — запись с:

  * `offset` — где в секции нужно править.
  * `type` — какой тип релокации (например `R_X86_64_PC32`, `R_X86_64_64` и т.д.).
  * `symbol` — индекс в `.symtab` (имя внешнего символа).
  * `addend` — дополнительное смещение.
* Пример: если в `foo.c` есть `extern int x; int f() { return x; }` — в `.text` появится инструкция, которая загружает адрес `x` через GOT; в `.rela.text` будет запись, говорящая линкеру «надо подставить адрес символа x в эту позицию».

## 2) Связывание объектников в `.so` (ld, либо `gcc -shared` как wrapper)

### Команда

```bash
gcc -shared -o libfoo.so foo.o bar.o -Wl,-soname,libfoo.so.1
```

`gcc` вызывает линкер (`ld`) с опциями. `-shared` говорит: создаём `ET_DYN` (shared object).

### Задачи линковщика

1. **Объединить секции** `.text/.data` из всех `.o` в итоговые сегменты.
2. **Разрешить внутренние символы**: если один объект определяет `f` и другой использует `f`, то связываются внутренне.
3. **Создать динамические таблицы**:

   * `.dynamic` — динамическая секция с тегами DT_* (DT_NEEDED, DT_SONAME, DT_HASH/DT_GNU_HASH, DT_STRTAB, DT_SYMTAB, DT_RELA, DT_INIT/FINI и др.)
   * `.dynsym` — таблица символов, видимая в рантайме (те символы, которые могут потребоваться загрузчику/другим модулям). По ней `dlsym` и runtime линкер ищут имена.
   * `.dynstr` — строки имён для `.dynsym`.
   * `.gnu.hash` или `.hash` — индекс для быстрого поиска символов.
4. **Создать PLT и GOT**:

   * **GOT** (Global Offset Table) — таблица адресов (данные), которая содержит адреса глобальных переменных и адреса функций (после релокации).
   * **PLT** (Procedure Linkage Table) — косвенные переходы для вызова внешних функций, использующие GOT. PLT позволяет отложить связывание (lazy) и сделать вызовы универсальными.
5. **Создать релокации для рантайма**:

   * `.rela.plt` — релокации, применяемые ко входам PLT (JUMP_SLOT).
   * `.rela.dyn` — другие релокации (RELATIVE, GLOB_DAT и т.д.).
6. **Заполнить DT_NEEDED** — список зависимых shared libraries, которые нужны (если объект ссылался на внешние символы из libc и т. п.)
7. **Опционально разрешить или оставить нерешёнными внешние символы**:

   * По умолчанию при создании `.so` можно оставить некоторые символы нерезолвированными — тогда они будут решаться при загрузке `.so` (либо через DT_NEEDED зависимости).
   * Линкер может ругаться на неразрешённые символы при опции `-Wl,-z,defs` (требовать, чтобы на этапе линковки всё было разрешено).

### Что именно меняется по сравнению с `.o`

* `.symtab` (полная) остаётся; но **динамическая** таблица `.dynsym` формируется из символов, которые будут экспортироваться/видимы в runtime. Линкер решает, какие символы попадут в `.dynsym` (экспортируемые) — остальные остаются в `.symtab` только для отладки.
* Релокации из `.o` объединяются и преобразуются в `.rela.dyn`/`.rela.plt` — инструкции о том, какие места нужно править при загрузке.
* PLT/GOT добавляются — для внешних (неразрешённых) вызовов создаются отдельные записи.

## 3) Что записывает линкер в ELF `.so` — важные таблицы и теги

* ELF Header — тип `ET_DYN`.
* Program Headers (`PT_LOAD`) — указывают что нужно мапить в память (в секции, page-aligned).
* `.dynamic` — набор записей DT_*, например:

  * `DT_NEEDED` — имена зависимостей (libc.so.6 и т. д.).
  * `DT_SONAME` — строка с именем библиотеки, например `libfoo.so.1` (SONAME используется загрузчиком для сопоставления версий).
  * `DT_STRTAB`, `DT_SYMTAB`, `DT_RELA`, `DT_JMPREL`, `DT_INIT_ARRAY` и т.д.
* `.dynsym` / `.dynstr` — динамические символы и их имена.
* `.gnu.hash` или `.hash` — хеш-таблица для быстрого поиска символов.
* `.rela.plt` и `.rela.dyn` — релокационные записи, которые загрузчик применит.
* PLT и GOT — код и таблицы для косвенных вызовов.

## 4) Что такое релокации и как их обрабатывает linker vs loader

### В `.o` релокации говорят:

> «В этом месте нужно вставить адрес символа X при окончательной компоновке.»

При создании `.so` линкер:

* для тех символов, которые он может разрешить (определены в предоставленных `.o`), он заменит/применит релокации на этапе линковки (link-time relocations).
* для внешних символов (например `printf`) — он оставит *референсы* и создаст записи в `.rela.plt`/`.rela.dyn`, чтобы загрузчик (ld.so) мог выполнить релокации при `dlopen`/загрузке или при первом вызове PLT (если lazy).

### Типы релокаций на x86_64 (примеры)

* `R_X86_64_JUMP_SLOT` — PLT entry для функции; заполняется адресом целевой функции.
* `R_X86_64_GLOB_DAT` — инициализация GOT для глобальных переменных.
* `R_X86_64_RELATIVE` — относительная релокация: установка адреса относительно базы.
* `R_X86_64_64` — простая 64-битная запись абсолютного адреса.

## 5) PIC vs non-PIC и роль GOT/PLT

* **PIC**: код использует инструкции, которые не содержат абсолютных адресов; для обращения к глобальным переменным используется GOT (индирекция): сначала прочитать адрес переменной из GOT, затем использовать его. Для вызовов внешних функций используют PLT, который при первом обращении вызывает динамический резолвер и затем обновляет GOT/PLT на прямой адрес.
* **non-PIC**: компилятор может встроить абсолютные адреса прямо в инструкции (fast but fixed). Для .so это плохо — требует правки кода при загрузке (text reloc), делает код не разделяемым.

## 6) SONAME, DT_NEEDED, версия символов

* `-Wl,-soname,libname.so.1` задаёт **SONAME** — это то имя, которое `ldconfig` и загрузчик будут использовать при разрешении ссылок `DT_NEEDED`.
* `DT_NEEDED` указывает, какие библиотеки требуются для работы (например libc).
* Символы могут иметь версионирование (GNU symbol versioning) — используется в крупных библиотеках.

## 7) Как всё потом используется при `dlopen`/загрузке (кратко)

1. Loader читает Program Headers (`PT_LOAD`) → делает `mmap` соответствующих сегментов с правильными правами.
2. Loader парсит `.dynamic` → находит `.dynsym`, `.dynstr`, `.rela.*`.
3. Loader применяет релокации из `.rela.dyn` и `.rela.plt` (по флагам RTLD_NOW/Lazy).
4. Loader вызывает `init` функции (`.init_array`).
5. `dlsym` использует `.dynsym`/`.dynstr` и `.gnu.hash` для поиска символа и возвращает `st_value + base`.

## 8) Как смотреть содержимое `.o` и `.so` (полезные инструменты)

* `readelf -h libfoo.so` — ELF header
* `readelf -l libfoo.so` — program headers (PT_LOAD — смещения и виртуальные адреса)
* `readelf -S libfoo.so` — section headers
* `readelf -d libfoo.so` — dynamic section (DT_* tags, DT_NEEDED, SONAME)
* `readelf -s libfoo.so` — symbol table (`.dynsym`/`.symtab` depending)
* `objdump -d libfoo.so` — дизассемблирование
* `nm -D libfoo.so` — динамические символы
* `objdump -x` — много информации о заголовках
* `readelf --debug-dump=info` — отладочная информация (DWARF)

Пример:

```bash
readelf -l libmath_dl1.so    # увидишь PT_LOAD и file offsets -> свяжешь с mmap offset
readelf -s libmath_dl1.so | grep Pi
readelf -d libmath_dl1.so    # DT_NEEDED, SONAME, DT_RELA, DT_JMPREL
```

---

## 9) Почему linker может оставить нерезолвованные символы в `.so`

* Для разделяемых библиотек часто разрешают нерешённые внешние символы — чтобы разрешать их при загрузке приложения или через DT_NEEDED. Это позволяет собирать плагины, которые будут зависеть от хоста. Если хочешь требовать, чтобы все символы были разрешены при сборке `.so`, используй флаг:

```bash
-Wl,-z,defs
```

(тогда линкер вернёт ошибку на неразрешённые символы).

## 10) Практические рекомендации / чек-лист при создании `.so`

1. **Компиляция исходников в `.o`**:

   * всегда используйте `-fPIC` для .so:

     ```bash
     gcc -fPIC -c math_dl1.c -o math_dl1.o
     ```
2. **Линковка в `.so`**:

   * создавайте .so с `-shared` и указывайте SONAME:

     ```bash
     gcc -shared -o libmath_dl1.so math_dl1.o -Wl,-soname,libmath_dl1.so
     ```
3. **Контроль экспортируемых символов**:

   * (опционально) скрывайте не нужные символы с `-fvisibility=hidden` и используйте `__attribute__((visibility("default")))` для экспортируемых API.
   * или используйте **version script** (.map) для явного экспорта.
4. **Проверяйте содержимое**:

   * `readelf -d libmath_dl1.so`, `readelf -s libmath_dl1.so`, `objdump -T libmath_dl1.so`.
5. **Проверяйте зависимости**:

   * `ldd libmath_dl1.so` покажет DT_NEEDED зависимости.
6. **При проблемах с поиском symbol**:

   * проверь `.dynsym` — если символ есть в `.symtab` но не в `.dynsym`, `dlsym` не найдёт его. Линкер решает, какие символы попадут в `.dynsym`.

## 11) Небольшой практический пример и выводы

Создаём минимальную библиотеку:

`math.c`

```c
#include <stdio.h>
float Pi(int K) { /*...*/ }
char* translation(long x) { /*...*/ }
```

Команды:

```bash
gcc -fPIC -c math.c -o math.o
gcc -shared -o libmath.so math.o -Wl,-soname,libmath.so
readelf -d libmath.so        # динамическая секция
readelf -s libmath.so | grep Pi
```

Проверяем, что `Pi` присутствует в `.dynsym`. Если `readelf -s` находит Pi только в `.symtab`, но не в `.dynsym`, `dlsym` не сможет её найти. Чтобы гарантировать экспорт, убедись, что символ не помечен как локальный/hidden.

## 12) Короткие ответы на частые вопросы

* **Почему нужен `-fPIC`?** — чтобы код был позиционно-независимым и безопасным для общего использования и без текстовых релокаций.
* **Что такое GOT/PLT?** — таблицы косвенной адресации: GOT — для данных и адресов, PLT — для вызовов функций. Они позволяют lazy- и fast-binding.
* **Кто заполняет релокации?** — linker создает записи релокаций; loader (ld.so) применяет их во время загрузки (или откладывает при lazy), подставляя реальные адреса.
* **Где хранится символ-имя?** — в `.dynstr`, `.dynsym` содержит индекс в `.dynstr` и `st_value` (offset) для адреса.
* **Как dlsym находит адрес?** — через хеш-таблицу (`.gnu.hash`/`.hash`) ищет строку в `.dynstr`, находит `Elf64_Sym`, берёт `st_value` и прибавляет базовый адрес mapping.
