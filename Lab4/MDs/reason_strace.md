Смотри, тут важно понять одну вещь:
**количество `mmap` при загрузке `.so` — это внутренняя кухня динамического загрузчика и раскладки ELF, а не “правильно/неправильно”.** У тебя 2 маппинга, у одногруппника 4, потому что по-разному разложены сегменты в `.so` и разные бинарные форматы (ARM64 vs x86-64) / версии линкера.

Разберём на конкретных кусках.

---

## 1. Как выглядит загрузка твоей `libimpl1.so`

Из твоего `strace` (ARM64):

```text
openat(AT_FDCWD, "./libimpl1.so", O_RDONLY|O_CLOEXEC) = 3
read(3, "\177ELF...", 832) = 832
fstat(3, ...) = 0
getcwd("/home/kyp/Downloads/lab4_8", 128) = 27

mmap(NULL, 69688, PROT_READ|PROT_EXEC, MAP_PRIVATE|MAP_DENYWRITE, 3, 0) = 0xffffae09c000
mprotect(0xffffae09d000, 61440, PROT_NONE) = 0
mmap(0xffffae0ac000, 8192, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_FIXED|MAP_DENYWRITE, 3, 0) = 0xffffae0ac000

close(3) = 0
```

Ключевое:

1. **Первый `mmap`** – большой кусок файла:

   ```text
   mmap(NULL, 69688, PROT_READ|PROT_EXEC, ..., fd=3, offset=0)
   ```

   Это, по сути, **код + константы + часть метаданных**, всё одним блоком, с правами `RX`.

2. Потом:

   ```text
   mprotect(..., PROT_NONE)
   ```

   Загрузчик защищает часть диапазона, чтобы потом поверх неё положить другие сегменты.

3. **Второй `mmap`**:

   ```text
   mmap(0xffffae0ac000, 8192, PROT_READ|PROT_WRITE, MAP_FIXED, fd=3, offset=0)
   ```

   Это данные (сегмент `.data`/`.bss`) с правами `RW`, замапленные поверх нужного куска.

То есть схема примерно:

* один `mmap` для **кода (.text) + rodata (R/X)**;
* один `mmap` для **данных (R/W)**.

Итого: **2 `mmap` на твою библиотеку — “толстый” для кода/rodata и отдельный для данных.**

## 2. Как выглядит загрузка чужой `libs/libmath_dl1.so`

У одногруппника (x86_64):

```text
openat(AT_FDCWD, "libs/libmath_dl1.so", O_RDONLY|O_CLOEXEC) = 3
read(3, "\177ELF...", 832) = 832
fstat(3, ...) = 0
getcwd("/work/Lab4", 128) = 11

mmap(NULL, 16448, PROT_READ, MAP_PRIVATE|MAP_DENYWRITE, 3, 0)       = 0x7f9fa9ff2000
mmap(0x7f9fa9ff3000, 4096, PROT_READ|PROT_EXEC, MAP_PRIVATE|MAP_FIXED|MAP_DENYWRITE, 3, 0x1000) = 0x7f9fa9ff3000
mmap(0x7f9fa9ff4000, 4096, PROT_READ, MAP_PRIVATE|MAP_FIXED|MAP_DENYWRITE, 3, 0x2000)          = 0x7f9fa9ff4000
mmap(0x7f9fa9ff5000, 8192, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_FIXED|MAP_DENYWRITE, 3, 0x2000) = 0x7f9fa9ff5000
close(3) = 0
mprotect(0x7f9fa9ff5000, 4096, PROT_READ) = 0
```

Здесь уже **4 `mmap`**:

1. `mmap(NULL, 16448, PROT_READ, ...)` — грубо говоря, “общий” read-only маппинг всего файла.
2. `mmap(..., PROT_READ|PROT_EXEC, ..., offset=0x1000)` — участок кода (`.text`), с правами RX.
3. `mmap(..., PROT_READ, ..., offset=0x2000)` — участок read-only данных (`.rodata`).
4. `mmap(..., PROT_READ|PROT_WRITE, ..., offset=0x2000)` — участок `.data`/`.bss` с R/W (частично поверх того же диапазона).

То есть линковщик/загрузчик на x86-64 выбрал более “тонкую” схему:

* отдельный RX-сегмент для кода,
* отдельный R-сегмент для констант,
* отдельный RW-сегмент для данных,
* плюс исходный read-only маппинг всего файла.

---

## 3. Почему так: от чего зависит количество `mmap`

Количество `mmap` на `.so` определяется:

1. **Разметкой ELF-файла по сегментам (Program Headers, PT_LOAD)**

   * Сколько сегментов “нагрузки” (`PT_LOAD`) с разными флагами (R/X/W) сформировал линкер.
   * На ARM и x86-64 линкер и glibc могут использовать разные эвристики.

2. **Версией/настройками линкера (`ld`, `gold`, `lld`)**

   * Один может склеивать `.text` и `.rodata` в один сегмент,
   * другой — отделять `.rodata` от `.text` для защиты от исполнения/перезаписи.

3. **Архитектура и требования к выравниванию страниц**

   * ARM64 vs x86-64 — немного разные ABI и, как следствие, разные дефолтные сегментные раскладки.

4. **Оптимизации по безопасности**

   * Отдельные R-only сегменты для данных → сложнее эксплуатировать переполнение.
   * Отдельные RW и RX сегменты → “W^X” политика (не одновременно Writable и Executable).

В твоём случае:

* ELF, который тебе сгенерировал `cc` с `-shared -fPIC`, на ARM64 даёт **два PT_LOAD сегмента**:

  * один RX (код + rodata),
  * один RW (data/bss).

У одногруппника:

* его линкер на x86-64 врубил более детализированную схему, и загрузчик разбил это на несколько `mmap`.

---

## 4. Важно для лабы: нормально ли у тебя?

Да, абсолютно.
С точки зрения ТЗ:

* ты **создаёшь две `.so`**, реализующие контракты;
* у тебя есть программа №2, которая:

  * грузит `.so` через `dlopen`,
  * достаёт функции через `dlsym`,
  * по `0` выгружает одну (`dlclose` + `munmap`) и загружает другую.

То, что:

* у тебя `dlopen` приводит к двум `mmap`,
* у него — к четырём,

никак не говорит о корректности / некорректности: это просто различие в том, **как именно динамический загрузчик и ядро разбивают ELF на участки памяти**.

Можно даже красиво сформулировать в отчёте:

> При анализе `strace` видно, что на ARM64 для подключения каждой библиотеки выполняются два вызова `mmap` (RX и RW сегменты), тогда как на x86-64 — четыре `mmap` (разделение на код, константы и данные). Это различие обусловлено разной разметкой ELF-сегментов и реализацией динамического загрузчика, а не логикой программы.

Если хочешь, можно отдельно посмотреть `readelf -l libimpl1.so` и сопоставить конкретные `PT_LOAD` сегменты с этими `mmap` — это прям идеально зайдёт в текст лабораторного.
