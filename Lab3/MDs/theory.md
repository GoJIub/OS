# 1. Что такое **shared memory (разделяемая память)**

**Shared memory (разделяемая память)** — это механизм межпроцессного взаимодействия (IPC), при котором **несколько процессов получают доступ к одному и тому же участку физической памяти**.

Процессы видят этот участок как часть своего адресного пространства, но физические страницы памяти **общие**.

Иначе говоря:

> Shared memory — это самый быстрый способ обмена данными между процессами, потому что данные вообще нигде не копируются.

---

# 2. Как работает shared memory на уровне ОС

## 2.1. Стандартный механизм POSIX: `shm_open` + `mmap`

Рабочий pipeline:

1. Процесс вызывает **`shm_open(name, flags, mode)`**
   → файл создаётся в `/dev/shm` (Linux) или в tmpfs.

2. Процесс вызывает **`ftruncate()`**
   → задаёт размер разделяемого объекта.

3. Процесс вызывает **`mmap(fd, PROT_READ|WRITE, MAP_SHARED, ...)`**
   → отображает этот объект в своё адресное пространство.

4. Другие процессы вызывают **`shm_open`** с тем же именем
   → получают тот же объект.

5. Они тоже делают **`mmap` → получают В ТОТ ЖЕ участок физической памяти**.

ОС создаёт **один набор физических страниц**, но отображает их в адресные пространства нескольких процессов.

---

# 3. Главное отличие shared memory от pipe/queue/socket

| Механизм          | Что делает                                                       |
| ----------------- | ---------------------------------------------------------------- |
| **pipe / socket** | Данные **копируются** ядром из процесса А в процесс Б            |
| **shared memory** | Данные **не копируются**, оба процесса видят один и тот же буфер |
| **message queue** | Данные отправляются/хранятся в очереди (копируются)              |
| **файлы**         | Системные вызовы I/O (медленно), данные проходят через кэш ядра  |

Shared memory — **самый быстрый** IPC-механизм.

Но у него проблема:
**нет автоматической синхронизации**, процессы могут перезаписывать данные друг друга.

Поэтому shared memory ВСЕГДА используют вместе с:

* **семафорами (sem_t)**
* **мьютексами (pthread_mutex_t с атрибутами PTHREAD_PROCESS_SHARED)**
* **futex**
* **барьерами**

---

# 4. Где хранится shared memory

Зависит от ОС:

### Linux

Shared memory POSIX создаётся в **tmpfs** — обычно каталог:

```
/dev/shm/
```

Там лежат файлы со специальными атрибутами.

### SysV shared memory (старый вариант)

Использует структуры ядра (`shmid`, `shmat`, `shmdt`) — без файлов.

---

# 5. Зачем нужна shared memory

### 5.1. Максимальная скорость IPC

Потому что:

* нет системных вызовов при чтении/записи,
* нет копирования данных в ядре,
* нет переключения контекста.

### 5.2. Передача больших массивов данных

Например:

* видео-фреймы,
* большие матрицы,
* графы,
* результаты ML-моделей,
* буферы сетевых пакетов.

### 5.3. Работа в режиме “producer/consumer”

Например:

* процесс А производит данные (записывает в память),
* процесс Б их читает.

---

# 6. Как может сломаться shared memory

Shared memory — мощный инструмент, но легко ошибиться.

### 6.1. Race conditions

Если два процесса пишут в один буфер без mьютексов → данные повреждаются.

### 6.2. Взаимоблокировки

Если использовать семафоры неправильно (например, не симметрично up/down).

### 6.3. Разные процессы видят разные структуры

Ошибки в layout памяти:

* разные размеры структур,
* разные выравнивания,
* разная версия ПО,
* UB при доступе.

### 6.4. Процесс упал и оставил семафор занятым

Может случиться deadlock, если семафор не “robust”.

### 6.5. Утечки shared memory объектов

Если забыть `shm_unlink()`, память остаётся в `/dev/shm`.

# 1. Что такое FAT и как он устроен

**FAT (File Allocation Table)** — это семейство файловых систем, использующее таблицу размещения файлов. Самые известные варианты: FAT12, FAT16, FAT32, exFAT.

### Ключевые идеи FAT

1. **Диск разбит на кластеры.**

   * Кластер — минимальная единица хранения (несколько секторов).

2. **Основная структура FAT — это таблица, где каждая строка — это кластер.**

   * Каждая запись FAT говорит:

     * кластер занят/свободен,
     * какой кластер идёт следующим в цепочке файла,
     * или это конец файла (EOF).

3. **Файл — это связный список кластеров.**

   * Директория хранит номер первого кластера.
   * FAT говорит, куда идти дальше.

4. **Схема хранения:**

   * **Boot Sector** — параметры файловой системы.
   * **FAT1, FAT2** — две копии таблицы (в FAT32 используются резервные копии).
   * **Root directory** (в FAT32 — обычный каталог).
   * **Data region** (кластерное пространство).

### Пример цепочки

Если файл занимает 3 кластера, FAT может быть:

```
5 -> 7 -> 12 -> EOF
```

### Особенности FAT

* Очень простая реализация.
* Плохо масштабируется (большие фрагментации).
* Нет журналирования, поэтому используются только на флешках, SD-картах, BIOS.

# 2. Как в strace доказать, что mmap отображает именно мой shared memory

Ты должен указать **два факта**:

### **Факт 1: openat открывает /dev/shm/shm_data и возвращает fd = X**

В strace:

```
openat(AT_FDCWD, "/dev/shm/shm_data",
       O_RDWR|O_CREAT|O_NOFOLLOW|O_CLOEXEC, 0666) = 3
```

→ значит файловый дескриптор **3** принадлежит твоему объекту shared memory.

Также:

```
openat(AT_FDCWD, "/dev/shm/shm_err", ...) = 4
```

→ fd=4 — объект для логов.

### **Факт 2: mmap использует этот же fd (3 и 4)**

В strace:

```
mmap(NULL, 1088, PROT_READ|PROT_WRITE, MAP_SHARED, 3, 0) = 0xffffa7b6b000
mmap(NULL, 4128, PROT_READ|PROT_WRITE, MAP_SHARED, 4, 0) = 0xffffa7b69000
```

→ Вызов mmap **отображает память именно из fd=3 и fd=4**, которые ранее вернул openat.

# 3. Что значат флаги PROT_READ | PROT_WRITE? Что такое PROT?

В mmap есть аргумент **prot** — это битовая маска, определяющая **разрешения доступа** к отображаемой памяти.

### Основные значения PROT_*

* **PROT_READ** — разрешает чтение из отображения.
* **PROT_WRITE** — разрешает запись.
* **PROT_EXEC** — разрешает выполнение кода.
* **PROT_NONE** — запрещает любые операции.

### PROT — это:

**Набор битовых флагов, определяющих права доступа к страничному отображению файла в память.**

Фактически, ядро выставляет атрибуты страниц таблицы памяти (PTE):

* R/W биты,
* X биты (в системах с NX-bit).

### В твоём коде используется:

```c
PROT_READ | PROT_WRITE
```

Это означает:

**«Данный участок mmap можно и читать, и писать»**,
что логично, так как parent и child модифицируют структуры в shared memory.

# 4. Почему shm_unlink стоит перед открытием shm_open?

На самом деле, **в правильном коде shm_unlink должен стоять ПОСЛЕ работы** — и у тебя всё правильно: unlink вызывается в конце.

Но иногда в примерах (и в учебных материалах) делают так:

```c
shm_unlink("/my_shm");
shm_open("/my_shm", O_CREAT|O_RDWR, 0666);
```

Почему так?

### **Причина 1. shm_unlink удаляет предыдущий объект, если программа упала**

`shm_open` создаёт объекты в `/dev/shm`. Если программа завершилась аварийно и забыла удалить объект, повторный запуск столкнётся с «мусором».

Поэтому защитный приём:

```
shm_unlink(name) — удалить старый объект, если есть
shm_open(name) — создать новый чистый объект
```

Это то же самое, что:

```
unlink("myfifo");
mkfifo("myfifo");
```

в работе с именованными каналами.

### **Причина 2. shm_unlink не уничтожает объект немедленно**

* Он помечается как «удалённый», но остаётся до тех пор, пока все процессы его не закроют.
* Поэтому никаких гонок с shm_open нет.

### **Ответ для защиты**

> shm_unlink перед shm_open используется как защитная мера: если после предыдущего запуска в `/dev/shm` остался объект с таким же именем, он будет удалён. Это позволяет гарантировать, что программа работает с «чистой» shared memory, а не с остатками старого сегмента.

## A. По shared memory и mmap

**1. Чем отличается mmap от обычного malloc?**

* `malloc` выделяет частную виртуальную память процесса.
* `mmap` может отображать файл, устройство или анонимную память.
* При `MAP_SHARED` — это механизм взаимодействия между процессами.

**2. В чём разница между MAP_SHARED и MAP_PRIVATE?**

* MAP_SHARED — изменения отражаются в файле и видны другим процессам.
* MAP_PRIVATE — copy-on-write, изменения видит только процесс.

**3. Что будет, если два процесса одновременно напишут в shm_data->buf без семафора?**

* Data race → undefined behavior.
* Содержимое может быть частично перезаписано, т.к. запись не атомарная.

---

## B. По POSIX семафорам

**4. Почему sem_init требует pshared=1?**

* Чтобы семафор был доступен *между процессами*, а не между потоками.

**5. Что делает семафор sem_full в твоей работе?**

* Гарантирует, что child не будет читать из буфера, пока parent туда не написал данные.

**6. Зачем нужен семафор sem_err?**

* Чтобы два процесса не писали в лог ошибок одновременно (синхронизация доступа).

---

## C. По файловым системам, ОС и дескрипторам

**7. Что такое файловый дескриптор?**

-Целое число, указывающее на открытый объект ядра: файл, сокет, shared memory.

**8. Почему /dev/shm — это tmpfs?**

* Потому что POSIX shared memory — просто файлы в tmpfs, хранящиеся в RAM.

---

## D. По strace / системным вызовам

**9. Что показывает clone(... SIGCHLD ...)?**

* Это системный вызов, которым реализуется fork().

**10. Как в strace увидеть передачу данных через shared memory?**

* Никак напрямую — *данные передаются без системных вызовов*, напрямую через память.
* Но можно увидеть семафоры (futex) и mmap/open.

---

## E. Специально по твоей лабораторной

**11. Как родитель передаёт имя файла дочернему?**

* Через shm_data->buf.
* Child делает sem_wait(sem_full) → читает данные → sem_post(sem_empty).

**12. Как child перенаправляет вывод в файл?**

```c
dup2(fd, STDOUT_FILENO);
```

**13. Какой системный вызов в strace показывает эту операцию?**

`dup2` → `dup3` или `fcntl(F_DUPFD)` в зависимости от ОС.

**14. Где видно, что ошибка записывается в shm_err?**

* В strace это не отражается напрямую (обычная запись в память).
* Но видно вызов `sem_wait(sem_err)` через `futex`.

# 1. Что такое i-узел (inode)

Это **структура метаданных файла**, хранящая:

* права доступа, uid/gid
* тип объекта (файл/директория/устройство)
* размер
* время создания/изменения/доступа
* указатели на блоки данных

Имена файлов **не хранятся в inode** — они живут в каталогах.
Каталог — это таблица типа:

```
имя → номер inode
```

---

# 2. Что такое hardlink (жёсткая ссылка)

Hardlink — это **ещё одна запись в каталоге**, указывающая на **тот же самый inode**.

То есть:

```
file1 ----> inode #123
file2 ----> inode #123   (hardlink)
```

Обе записи указывают на один и тот же i-узел.

### Ключевые свойства:

1. **И один и другой — полноценные имена файла.**
2. Данные и метаданные общие.
3. У файла появляется **дополнительный счётчик ссылок** (link count) в inode.
4. Удаление имени → уменьшается link count, но inode и данные живут, пока count > 0.
5. Жёсткие ссылки можно создавать:

   * только **в пределах одного файлового раздела (FS)**,
   * но нельзя на каталоги (в Unix — запрещено для предотвращения циклов).

### Характеристика в контексте inode:

* Hardlink = **ещё одна запись имя → тот же inode**.
* Один inode может иметь **несколько имён**.
* inode "живет", пока его link count > 0.

---

# 3. Что такое softlink (символическая ссылка, symlink)

Softlink — это **специальный файл**, у которого **собственный inode**, а внутри него **хранится путь к другому файлу**.

Структура:

```
link.txt ----> inode #777 (тип: symlink)
                     |
                     | содержит строку "path/to/file"
                     v
                 file ----> inode #123
```

### Характеристики:

1. Имеет **свой собственный inode**, отличный от цели.
2. В его блоках данных хранится **строка-путь**, а не данные файла.
3. Может ссылаться:

   * на файл в другом разделе,
   * на каталог,
   * на несуществующий файл (broken link).
4. При удалении оригинала softlink ломается.

### Характеристика в контексте inode:

* Softlink = **другой inode**, тип "symlink".
* В inode symlink либо:

  * inline хранятся данные (до 60 байт), либо
  * в блоках данных хранится путь.

---

# 4. Краткая таблица — именно как отличить через i-узлы

| Свойство                                   | Hardlink                | Softlink                                     |
| ------------------------------------------ | ----------------------- | -------------------------------------------- |
| Количество inode                           | **один общий inode**    | **у ссылки свой inode**                      |
| Содержимое inode                           | Данные файла            | Тип: symlink, данные = путь                  |
| Увеличивает link count?                    | Да                      | Нет                                          |
| Может указывать на файл на другом FS?      | Нет                     | Да                                           |
| Может указывать на каталог?                | Почти никогда           | Да                                           |
| Ломается при удалении оригинального файла? | Нет                     | Да                                           |
| Влияет на права доступа цели?              | Нет (те же права inode) | Может не иметь доступа, если путь недоступен |

### Hardlink

```
$ ls -li

12345 -rw-r--r-- 2 user user  100 file2
```

Один и тот же inode **12345**, link count = **2**.

### Softlink

```

```

Разные inode (12345 и 54321), символическая ссылка типа `l`.

# 1. Что такое журнал в файловой системе (Journal)

**Журнал (journal)** — это выделенная область в файловой системе, куда **записываются операции изменения данных и метаданных перед фактической записью в основную часть диска**.

Другими словами:

> Журнал — это «чёрный ящик» или «лог» изменений файловой системы, позволяющий восстановить её после сбоя.

Используется в **журналируемых FS**:

* ext3, ext4
* XFS
* ReiserFS
* JFS
* NTFS (имеет свой журнал MFT records)
* ZFS/Btrfs используют другой подход (copy-on-write), но по сути решают ту же задачу.

---

# 2. Зачем нужен журнал (основная мотивация)

Без журналирования (ext2, FAT):

* Если пропало питание **во время записи**, файловая система оказывается в *неконсистентном состоянии*.
* После перезагрузки требуется **fsck** (длинная проверка всего диска).
* Возможно:

  * потеря данных,
  * повреждённые каталоги,
  * «висящие» inodes,
  * утечки блоков.

Журналирование решает:

## 2.1. Быстрое восстановление после краша

При загрузке ОС читает журнал:

* смотрит, какие операции были *запланированы*, но *не завершены*;
* либо **откатывает** их (rollback),
* либо **повторяет** (redo), если они почти дошли до конца.

FS становится консистентной за **миллисекунды**.

## 2.2. Стабильность метаданных

Журнал защищает:

* суперблок,
* таблицу i-узлов,
* битовые карты свободных блоков,
* структурные записи каталогов.

## 2.3. Способность пережить внезапные выключения питания / kernel panic

Журнал гарантирует, что FS не окажется «полурасписанной».

---

# 3. Как работает журнал (механика)

Механизм общий для журналируемых систем:

### Шаг 1 — Создание транзакции

Изменения группируются в **транзакцию**:

* изменение i-node
* изменение bitmap
* вставка записи каталога
* выделение/освобождение блоков
* запись данных (иногда)

### Шаг 2 — Запись транзакции В ЖУРНАЛ

Перед внесением изменений в реальную FS они записываются как:

* списки блоков
* новые значения
* контрольные суммы

Журнал всегда пишется **последовательно**, что быстро для HDD/SSD.

### Шаг 3 — Коммит в журнал

Когда все записи транзакции в журнал попали на диск — происходит **commit record**.

Теперь журнал говорит:
«Эта операция гарантированно была полностью записана».

### Шаг 4 — Реплей или отмена

После commit ядро спокойно записывает изменения и в реальную структуру FS.

Если произошёл сбой:

* OS смотрит записи журнала
* применяет их (redo) или игнорирует незакоммиченные (abort)

# 4. Где физически хранится журнал

Это либо:

* **внутри файловой системы** (ext3/ext4 default),
* **на отдельном разделе или устройстве** (вариант ext4 external journal).

Внутренний журнал — часть FS, просто отдельный набор блоков.

---

# 5. Виды журналирования (на примере ext3/ext4)

## 5.1. journal (full data journaling)

В журнал пишутся:

* **и данные файла**,
* **и метаданные**.

Самый надёжный режим, но медленнее.

## 5.2. ordered (по умолчанию в ext4)

В журнал пишутся:

* **только метаданные**

Но запись данных файла **гарантированно происходит ДО коммита метаданных**.

Это защита от появления «мусора» в файлах.

## 5.3. writeback

В журнал пишутся:

* только метаданные

Но порядок записи данных **не гарантируется**,
поэтому возможны «грязные» блоки после сбоя.

Это самый быстрый, но менее надёжный режим.

---

# 6. Что журнал НЕ защищает

* Не защищает от **аппаратных ошибок SSD/HDD**.
* Не защищает от случайного удаления файлов.
* Не защищает от повреждения блока данных, если он уже записан.
* Не защищает от silent data corruption (этим занимается ZFS/Btrfs).

Журнал — это только **метод атомарности** структур FS.

---

# 7. Как может сломаться журнал

Теоретически:

1. Повреждение самого журнала → реконструкция через fsck -f.
2. Метаданные корректны, но данные файла могут содержать старый мусор → особенно в writeback mode.
3. Если SSD использует агрессивный кеш без FTL-синхронизации, возможны «выравнивания» и неожиданное reorder.

Однако повреждения **редки**, и журналирование на порядки надёжнее ext2/FAT.

---

# 8. Короткое резюме (идеально для устного ответа)

**Журнал — это лог изменений файловой системы.
Перед записью структур (inode, каталоги, bitmap) FS сначала пишет операции в журнал, фиксирует коммит, и только потом вносит изменения в основную область.
В случае сбоя журнал позволяет быстро восстановить согласованное состояние — откатить или повторить операции.**

---

1. Что такое суперблок
Суперблок — это главная структура метаданных файловой системы ext.
Он содержит всю ключевую информацию, необходимую ядру для работы с FS:
Суперблок хранит:
размер файловой системы (число блоков);
размер блока (1 KB / 2 KB / 4 KB);
число i-узлов;
число свободных i-узлов;
число свободных блоков;
UUID файловой системы;
время последнего монтирования, последнего fsck;
флаги состояния (чисто/грязно);
параметры журнала (ext3/ext4);
метаданные о группах блоков;
версию FS, поведение allocators и т. д.
Без суперблока FS недоступна, потому что ядру нечем руководствоваться при интерпретации структуры.

---

3. Что общего у всех ext
ext — это классическая Unix-подобная FS, основанная на:
1. inode
   Хранит:
   размер,
   права,
   uid/gid,
   метаданные,
   указатели на блоки данных.

2. Каталоги
   Хранят map:
   имя файла → inode number

3. Группы блоков
   Файловая система делится на block groups, каждая из которых содержит:
   суперблок (резервные копии),
   bitmap i-узлов,
   bitmap блоков,
   таблицу i-узлов,
   данные.
Это делает ext масштабируемой и ускоряет доступ.

---

Ты спрашиваешь про **однократный, двухкратный и трёхкратный косвенные блоки**
(**single / double / triple indirect blocks**) ― это ключевая часть структуры i-узла в ext2/ext3/ext4.

Ниже — **строго по делу и технически**, как это работает.

---

# 1. Что это такое (суть)

В классическом ext2/ext3 inode содержит **15 указателей на данные**:

```
12 прямых (direct)
1 однократный косвенный (single indirect)
1 двухкратный косвенный (double indirect)
1 трёхкратный косвенный (triple indirect)
```

Это делается для того, чтобы можно было хранить **очень большие файлы**, даже если один inode сам по себе маленький.

---

# 2. Прямые блоки (direct blocks)

Первых **12 указателей** inode → это прямые ссылки:

```
inode → data block
```

То есть каждый номер указывает **прямо на блок с данными файла**.

Используется для:

* маленьких файлов,
* первых килобайт/мегабайт больших файлов,
* быстрых операций чтения.

---

# 3. Однократный косвенный блок (**single indirect**)

Это указатель на блок, который содержит **массив номеров блоков данных**.

Структура:

```
inode → [single_indirect_block]
single_indirect_block → [data_block1, data_block2, data_block3, ...]
```

То есть используется дополнительный уровень косвенности.

Размер расширяется:
если блок = 4KB и номер блока = 4 байта →
в одном косвенном блоке помещается ~1024 адреса.

---

# 4. Двухкратный косвенный блок (**double indirect**)

Это указатель на блок,
который содержит указатели на другие косвенные блоки.

Структура:

```
inode → block_A
block_A → [block_B1, block_B2, ..., block_B1024]
block_Bi → [data1, data2, ..., data1024]
```

Таким образом можно адресовать:

```
1024 × 1024 = 1 048 576 блоков данных
```

---

# 5. Трёхкратный косвенный блок (**triple indirect**)

Ещё один уровень вложенности:

```
inode → block_L1
block_L1 → [block_L2_i]
block_L2_i → [block_L3_j]
block_L3_j → [data_k]
```

Количество адресуемых блоков:

```
1024 × 1024 × 1024 ≈ 1 млрд блоков
```

При размере блока 4 KB:

```
1 073 741 824 блоков × 4 KB ≈ 4 ТБ данных
```

То есть тройная косвенность позволяет хранить **гигантские файлы**.

---

# 1. Что такое i-узел (inode)

**i-узел (inode)** — это *основная структура метаданных файла* в Unix-подобных файловых системах (ext2/3/4, UFS, XFS, и т. д.).

Это **описатель файла**, который хранит *всю информацию о файле*, кроме имени.

Проще говоря:

> inode — это «паспорт файла», а имя файла — просто ссылка на этот паспорт.

---

# 2. Что хранится в inode

Inode содержит все **метаданные**, необходимые ядру для работы с файлом:

## 2.1. Адреса данных файла

Ссылки на блоки, где лежит содержимое файла:

* 12 прямых указателей (direct)
* 1 однократный косвенный (single indirect)
* 1 двухкратный косвенный (double indirect)
* 1 трёхкратный косвенный (triple indirect)

Это позволяет хранить файлы размером до гигабайтов и терабайтов.

## 2.2. Метаданные файла

* размер файла
* владелец (UID)
* группа (GID)
* права доступа (rwx)
* тип объекта (файл, каталог, симлинк, device node и т. д.)
* количество жёстких ссылок (hardlink count)
* время:

  * `ctime` — изменение метаданных
  * `mtime` — изменение содержимого
  * `atime` — последний доступ

## 2.3. Дополнительные данные

* флаги (immutable, append-only)
* расширенные атрибуты (xattr)
* ACL

---

# 3. Что inode **не** хранит

Самое важное:

## Inode не хранит имя файла!

Имена находятся **в каталогах**, которые представляют собой таблицу:

```
имя файла → номер inode
```

Поэтому:

* у файла может быть **несколько имён** (hardlinks)
* удалить имя ≠ удалить файл (если link count > 0)
* inode — это реальный объект файла, а имя — просто ярлык

---

# 4. Где хранятся inode

В ext-файловых системах пространство делится на **block groups**.
В каждой группе есть:

* bitmap inode
* таблица inode (inode table)
* bitmap блоков
* блоки данных

То есть inode хранятся в таблице размером фиксированных структур.

Размер inode (обычно 256–512 байт) задаётся при создании файловой системы.

---

# 5. Как ядро находит данные файла через inode

Процесс:

1. Через каталог ядро получает номер inode по имени файла.
2. По номеру inode находит запись в inode table.
3. Из inode читает:

   * права
   * тип
   * ссылки на блоки
4. С помощью указателей переходит к блокам данных на диске.

Это классический процесс **pathname resolution**.

---

# 6. Зачем нужен inode

## 6.1. Универсальная абстракция файла

И inode не зависит от имени, поэтому:

* можно переименовывать файл без изменения данных
* одно и то же содержимое можно ссылать разными именами

## 6.2. Надёжность

Inode обеспечивает строгую структуру хранения метаданных.

## 6.3. Быстрое восстановление

FS может проверять или восстанавливать damaged файловую систему, опираясь на таблицу inode.

## 6.4. Управление данными

Разные уровни прямых/косвенных ссылок позволяют эффективно хранить и маленькие, и огромные файлы.

---

# 7. Короткое объяснение (для зачёта)

**Inode — структура, которая хранит метаданные файла и ссылки на его блоки данных.
Имя файла не хранится в inode — оно лежит в каталоге, который связывает имя и номер inode.
Каждый файл имеет один inode, а каждый hardlink — это ещё одно имя, указывающее на тот же inode.**
